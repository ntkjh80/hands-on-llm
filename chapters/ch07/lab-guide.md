## 실습 목표와 실행 범위

이 실습은 모델 주변의 데이터 흐름을 직접 계산한다. 작은 벡터의 양자화, 단계별 템플릿 체인, 세 메모리 전략, 도구 실행 루프를 표준 Python으로 구현했다. 실제 LLM, LangChain, GGUF 모델, 외부 검색 API를 사용하지 않는다. 규칙형 코드가 만든 문장을 모델 생성 결과로 보고하지 않으며, 가상의 상품과 환율을 실제 정보로 사용하지 않는다.

원문과의 연결은 7장 PDF 281–284쪽의 모델 로딩, 285–293쪽의 체인, 293–306쪽의 메모리, 306–314쪽의 에이전트다. 이 장의 실제 모델·GPU·API 예제는 여기서 실행하지 않았다. 기본 개념을 재현하는 CPU 실습만 직접 실행하고 [실제 출력](lab-output.txt)을 저장했다.

## 실행

저장소 루트에서 다음과 같이 실행한다.

```bash
python3 chapters/ch07/lab.py
```

추가 설치나 인증 정보가 필요 없다. Python 3.9 이상을 기준으로 작성했으며 실행 환경에서 기본 실행과 변형 실행을 확인했다. 난수는 사용하지 않으므로 동일한 옵션과 코드는 같은 결과를 낸다.

```bash
python3 chapters/ch07/lab.py --help
python3 chapters/ch07/lab.py --window 1
python3 chapters/ch07/lab.py --window 3 --budget 20
python3 chapters/ch07/lab.py --lookup-fail-first --rate 0.90
python3 chapters/ch07/lab.py --max-steps 1
```

| 옵션 | 기본값 | 의미 |
|---|---:|---|
| `--window` | 2 | 최근에 완료된 대화 쌍의 수 |
| `--budget` | 35 | 과거 기록의 공백 단어 수 예산. 모델 토큰 수가 아님 |
| `--rate` | 0.85 | 교육용 EUR/USD 환율 |
| `--lookup-fail-first` | 꺼짐 | 첫 조회에 모의 오류를 반환 |
| `--max-steps` | 5 | 종료 결정을 포함한 도구 루프의 최대 반복 수 |

예산 초과는 표시만 한다. 프로그램이 초과 기록을 자동으로 잘랐다고 해석하면 안 된다. 이 구분 덕분에 보존된 정보와 예산 문제를 따로 관찰할 수 있다.

## 실습 1 작은 벡터 양자화

입력은 `[-1.0, -0.73, -0.31, -0.05, 0.13, 0.38, 0.67, 1.0]`이다. 최솟값과 최댓값 사이를 $2^b-1$개 간격으로 나누고 가까운 정수 코드로 바꾼 뒤 복원한다. (b)는 각 값의 비트 수다.

```math
s = \frac{x_{max}-x_{min}}{2^b-1},\quad
q_i = \mathrm{round}\left(\frac{x_i-x_{min}}{s}\right),\quad
\hat{x}_i=x_{min}+q_i s
```

평균제곱오차는 원래 값과 복원 값의 차이를 제곱해 평균한 값이다. 원래 벡터의 단위가 없는 이 교육용 예에서는 오차도 별도 물리 단위를 갖지 않는다.

| 비트 수 | 8개 값의 이상적 저장량 | 실제 실행 MSE |
|---:|---:|---:|
| 2 | 2 bytes | 0.03826806 |
| 4 | 4 bytes | 0.00137917 |
| 8 | 8 bytes | 0.00000162 |

이 표는 이 벡터와 이 양자화 규칙의 실제 계산 결과다. 특정 언어 모델의 정확도나 성능 점수가 아니다. 실제 GGUF의 저장 구조나 그룹별 양자화를 구현하지 않았고, 스케일·메타데이터 저장 비용도 표에서 제외했다.

**관찰 질문:** 왜 양 끝값은 이 예제에서 정확히 복원되는가? 구간의 양 끝을 직접 코드의 양 끝에 대응시켰기 때문이다. 가운데 값은 일정 간격의 격자 위에 놓이지 않을 수 있다.

**변경 실험:** 벡터에 큰 이상치 `10.0`을 추가해 보자. 같은 비트 수에서 간격이 커지면서 원래 작은 값의 오차가 어떻게 달라지는지 관찰한다. 실제 모델에서 이상치와 그룹별 스케일이 중요한 이유를 생각해 볼 수 있다. 변경한 결과는 기본 출력 파일과 구분해서 기록한다.

## 실습 2 체인의 입출력 계약

`story_chain`은 초기 소재를 받아 `title`, `character`, `story`를 차례로 만든다. 각 단계는 Python 문자열 서식만 사용한다. 이름은 이야기 체인이지만 창작 모델을 실행하지 않는다. 관찰할 대상은 각 단계의 `available_keys`다.

기본 실행에서는 키가 다음처럼 누적된다.

```text
summary
summary, title
summary, title, character
summary, title, character, story
```

`format_checked`는 템플릿에서 요구하는 필드를 읽고 실제 입력과 비교한다. 의도적으로 `title`을 빼는 예제에서는 `Missing fields: title`이 출력된다. 이 오류는 실습 실패가 아니라 경계 검사가 작동했다는 예상 결과다.

**손으로 추적하기:** 둘째 단계에서 `{title}`을 `{name}`으로 바꾸면 어느 검사에서 문제가 드러나는가? 답은 변수 치환 전 필수 키 검사다. 모델을 호출하지 않아도 발견할 수 있는 오류라는 점이 중요하다.

**확장 실험:** 별도 `review` 키를 추가해 이야기에 초기 소재가 포함되는지 검사하라. 문자열 포함 여부는 형식적 검사이며 이야기의 사실성이나 품질을 보증하지 않는다는 한계도 함께 적는다.

## 실습 3 메모리의 보존과 손실

대화는 여섯 번 진행된다. 첫 대화에 이름과 나이가 있고, 셋째는 이름을, 넷째는 나이를 묻는다. 다섯째에서 나이를 30으로 정정하고 거주 도시를 알려 준 뒤 여섯째에서 도시를 묻는다.

`full`은 모든 대화 원문을, `window`는 최근 대화 쌍을 입력에 붙인다. `summary`는 사용자의 명시적인 이름·나이·도시 문장을 정규식으로 추출해 짧은 사실 딕셔너리로 보존한다. 후자는 실제 LLM 요약의 품질을 재현하지 않는다. 정해진 영어 문장 패턴만 이해하며 복잡한 자연어·모순·부정·간접 표현은 처리하지 못한다.

| 기본 실행 관찰 | 전체 버퍼 | 최근 2턴 | 사실 요약 |
|---|---|---|---|
| 3번 이름 질문 | Mina | Mina | Mina |
| 4번 나이 질문 | 29 | 알 수 없음 | 29 |
| 6번 도시 질문 | Busan | Busan | Busan |
| 누적 과거 기록 단어 수 | 217 | 116 | 49 |

217·116·49는 이 규칙형 대화의 **실제 공백 단어 수 합계**다. 실제 토크나이저 토큰 수나 요금이 아니다. 요약 생성 비용도 포함하지 않는다. 따라서 이 결과만으로 실제 LLM 시스템의 세 전략 중 가장 싼 것을 결정할 수 없다.

**관찰 질문:** 왜 4번에서 이름이 아닌 나이를 물었는가? 3번 답변이 이름을 되풀이했기 때문에 이름은 최근 기록으로 다시 들어간다. 나이는 반복되지 않았으므로 첫 대화가 창 밖으로 나가면 사라진다.

**변경 실험:** `--window 1`이면 3번 호출에 첫 대화가 남지 않아 이름도 알 수 없게 된다. `--window 3`이면 4번 호출에 첫 대화가 남아 나이를 알 수 있다. 호출 직전의 기록을 기준으로 예상한 뒤 출력과 비교한다.

**예산 실험:** `--budget 20`으로 바꾸면 정보 보존 결과 자체는 그대로지만 초과 경고가 더 자주 나타난다. 저장 정책과 예산 판단이 별개라는 점을 확인한다. 실제 서비스로 확장할 때는 초과 시 창 축소·요약·명시적 오류 중 어떤 동작을 할지 설계해야 한다.

## 실습 4 도구 실행 루프

`agent_demo`는 정해진 정책을 가진 제어 루프다. 가격이 없으면 조회하고, 가격은 있지만 EUR 금액이 없으면 환산하며, 둘 다 있으면 종료한다. 조건 분기가 관찰된 상태에 따라 달라진다는 원리를 보여 준다. 실제 모델이 자율적으로 도구를 고르는 에이전트는 아니다.

기본 실행은 다음 순서다.

```text
lookup_price → USD 1200.00과 로컬 출처 확보
convert → 1200.00 × 0.85 = EUR 1020.00
finish → complete
```

금액은 `Decimal`로 계산하고 소수 둘째 자리로 반올림한다. 통화와 환율 방향을 명시했으므로 달러를 유로로 바꾸는 곱셈임을 확인할 수 있다. 상품은 가상의 StudyLaptop이며 실제 상품 가격을 조회하지 않는다.

`--lookup-fail-first`를 켜면 첫 조회가 오류를 반환한다. 상태에 가격이 아직 없으므로 다른 로컬 조회 항목을 사용한다. 로그에서 오류가 먼저 관찰되고 그 이후 다음 행동이 선택되는지를 확인한다.

`--max-steps 1`은 첫 조회만 진행하고 `incomplete`로 끝난다. 반복 한도는 성공을 강제하는 장치가 아니라 무한한 진행을 막는 장치다. `--max-steps 2`에서는 계산값이 있어도 명시적인 종료 단계까지 진행하지 않았으므로 역시 미완료로 표시한다. 종료 정책을 이해하고 로그를 읽어야 한다.

**설계 과제:** 가격 조회 결과에 통화가 누락됐을 때 환산 함수를 호출하지 않게 만들어 보자. 데이터가 없다는 것과 숫자가 0이라는 것을 구별해서 실패를 표현한다. 예상 답은 입력 검증에서 명시적인 오류를 만들고 완성된 금액으로 표시하지 않는 것이다.

## 원문의 실제 모델 실습으로 확장하는 순서

이 부분은 실행 절차의 설계 안내다. 현재 환경에서 아래 모델·API를 실제로 실행하거나 최신 호환성을 확인한 것은 아니다.

1. **모델과 엔진을 고른다.** 책은 GGUF Phi-3와 `llama-cpp-python`을 사용한다. 실제 선택한 파일의 정밀도를 확인한다. 원문의 FP16 파일은 8비트 설명과 일치하지 않는다.
2. **모델 하나를 먼저 호출한다.** 파일 로딩과 장치 지원을 확인하고, 해당 모델·인터페이스의 채팅 템플릿을 적용한다. 기록과 도구 없이 간단한 입력을 먼저 검증한다.
3. **템플릿의 완성 결과를 확인한다.** 변수 누락과 중복 역할 표지를 검사한다. 원문의 클래스 경로를 최신 패키지에 그대로 적용하기 전에 해당 버전의 공식 사용법을 확인한다.
4. **체인을 한 단계씩 연결한다.** 결과 키, 자료형, 빈 출력 처리, 최대 길이를 정한다. 중간 결과를 저장해 실패 시작점을 찾을 수 있게 한다.
5. **메모리를 추가한다.** 세션별 기록을 분리하고 실제 토크나이저로 길이를 측정한다. 전체 버퍼부터 시작해 필요한 손실 정책을 비교한다.
6. **요약 호출을 별도로 평가한다.** 최신 사실, 부정, 수치, 사용자 발언과 모델 추정의 구분을 확인한다. 응답 호출뿐 아니라 요약 호출의 비용도 센다.
7. **읽기 도구 하나부터 연결한다.** 원문은 웹 검색과 수학 도구를 사용한다. 도구 이름·입력·출력·오류 형식을 명시하고 실제 결과와 모델이 주장한 결과를 구별한다.
8. **실패와 종료를 평가한다.** 빈 검색, 잘못된 인수, 도구 오류, 반복 상한, 출처 누락을 포함해 확인한다. 한 번 성공한 예시만으로 신뢰성을 결론 내리지 않는다.

## 검증 범위

기본 실행, 창 크기 변경, 첫 조회 실패 후 복구, 반복 한도에 의한 미완료 종료를 직접 실행했다. 의미 있는 검산은 필수 필드 보존, 기본 창 크기에서 나이 정보의 소실, 전체 버퍼·사실 요약의 정보 유지, 완료된 환산 계산을 확인한다. 웹 검색 품질, 실제 LLM 추론 능력, 요약 모델 정확도, GGUF 성능은 이 검증 범위에 포함되지 않는다.
