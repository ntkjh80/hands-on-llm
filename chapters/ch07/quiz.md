# 7장 복습 문제와 해설

[전체 목차](../../README.md) · [학습 노트](study.md) · [강의안](lecture.md) · [강의 대본](lecture-script.md) · [시각화](visuals.html) · [실습](lab-guide.md) · [복습 문제](quiz.md)

총 16문항, 각 5점으로 80점이다. 해설을 열기 전에 자신의 설명과 계산을 적는다. 문장 암기보다 데이터 흐름과 조건을 설명하는 것이 중요하다. 원문 범위는 *Hands-On Large Language Models* 7장, PDF 물리 페이지 280–315쪽이다.

## 1. GGUF와 비트 수

파일 이름이 `model-fp16.gguf`다. “GGUF니까 4비트 양자화 모델이다”라는 말을 평가하라. 원문 283쪽에서 특히 확인할 내용도 적어라.

<details><summary>해설과 채점 기준</summary>

GGUF는 파일 형식이고 FP16은 16비트 부동소수점 정밀도를 나타내므로 이 주장은 틀렸다. 같은 형식의 파일에도 서로 다른 정밀도가 있을 수 있다. 원문 설명은 8비트 사용을 말하지만 실제 다운로드·로딩 코드는 FP16 파일을 가리킨다. 파일 형식과 정밀도 구분 2점, 실제 파일 확인 1점, 원문 불일치 설명 2점.

</details>

## 2. 가중치 저장량 손계산

가중치 30억 개를 16·8·4비트로 저장한다. 순수 가중치 데이터의 크기를 십진 GB로 계산하라. 이 값으로 실제 필요 메모리를 확정할 수 있는지도 설명하라.

<details><summary>해설과 채점 기준</summary>

크기는 가중치 수×비트 수÷8이다. 각각 6 GB, 3 GB, 1.5 GB다. 메타데이터, 양자화 스케일, 활성값, KV 캐시, 작업 버퍼 등이 추가되므로 전체 필요 메모리는 확정할 수 없다. 계산 각 1점, 식 1점, 추가 메모리 설명 1점.

</details>

## 3. 두 종류의 템플릿

업무 프롬프트의 `{product}` 변수와 Phi-3 예제의 사용자·어시스턴트 역할 표지는 무엇이 다른가? 모든 모델에 같은 역할 표지를 붙여도 되는가?

<details><summary>해설과 채점 기준</summary>

`{product}`는 업무에 따라 바뀌는 값을 넣는 자리다. 역할 표지는 모델의 대화 입력 형식을 구성한다. 전자는 요청 내용의 재사용을, 후자는 모델이 읽는 대화 경계를 다룬다. 모델·인터페이스마다 형식이 다를 수 있으며 API가 내부에서 처리할 수도 있다. 구분 3점, 모델별 형식·자동 처리 고려 2점.

</details>

## 4. 체인에서 사라진 키

제목 단계가 문자열 하나만 반환하고, 다음 인물 단계가 `summary`와 `title`이라는 두 키를 요구한다. 연결 기호만으로 실행하면 충분한가? 수정 방법을 제안하라.

<details><summary>해설과 채점 기준</summary>

충분하지 않다. 다음 단계가 기대하는 매핑이 없고 초기 `summary`도 사라질 수 있다. 입력 상태를 보존하고 새 결과를 `title` 키로 합친 뒤 다음 단계에 전달해야 한다. 프레임워크의 실제 반환 계약을 확인해야 하며 파이프 기호가 보존을 보장한다고 일반화하지 않는다. 불일치 진단 2점, 상태 병합 설계 2점, 계약 확인 1점.

</details>

## 5. 호출을 나누는 판단

한 번에 제목·인물·이야기를 만드는 방법과 세 번의 호출로 나누는 방법을 비교하라. 여러 단계가 항상 더 좋은지 구체적 제품 예를 들어 논하라.

<details><summary>해설과 채점 기준</summary>

여러 단계는 중간 산출물 재사용, 독립 수정, 형식 검증, 오류 추적에 유리하다. 그러나 호출 비용·지연이 늘고 앞 단계 오류가 전파될 수 있다. 제목을 별도 UI에 쓰고 인물을 수정하는 서비스는 분해 가치가 크다. 짧은 일회성 결과만 필요한 기능은 한 호출이 단순할 수 있다. 장점·비용 각 2점, 요구사항 기반 판단 1점. 결론만 쓰면 충분하지 않다.

</details>

## 6. 메모리와 학습

사용자 이름을 기억하게 만든 뒤 모델의 가중치 파일 크기가 변하지 않았다. 이상한 현상인가? 대화 메모리와 KV 캐시도 구분하라.

<details><summary>해설과 채점 기준</summary>

이상하지 않다. 이 장의 메모리는 외부 상태에 대화 정보를 저장하고 다음 입력에 다시 제공하므로 가중치 학습이 필요 없다. KV 캐시는 추론에서 처리한 토큰의 키·값 계산을 재사용하는 최적화다. 대화 기록의 의미적 보존·수명과는 목적이 다르다. 가중치와 상태 구분 3점, KV 캐시 역할 2점.

</details>

## 7. 창 크기 2의 손추적

첫 대화에서 이름과 나이를 알려 주고, 둘째에서 산술을 묻고, 셋째에서 이름을 물어 답변에 이름이 다시 등장했다. 넷째에서 나이를 묻는다. 이름과 나이 정보가 서로 다르게 남을 수 있는 이유를 설명하라.

<details><summary>해설과 채점 기준</summary>

넷째 호출 직전에 최근 두 대화는 둘째와 셋째다. 첫 소개는 빠졌지만 이름은 셋째 답변에서 새로 반복됐다. 나이가 다른 최근 메시지에 반복되지 않았다면 나이는 사라진다. 창은 사실의 중요도가 아니라 위치를 기준으로 원문을 선택한다. 호출 시점 추적 2점, 정보 재등장 2점, 위치 기반 정책 설명 1점.

</details>

## 8. 컨텍스트 예산

컨텍스트 한도가 4096토큰, 지시문·현재 질문·도구 설명이 900토큰, 출력 예약이 800토큰이다. 기록 예산은 얼마인가? 최근 3개 대화가 각각 900토큰이면 들어가는가?

<details><summary>해설과 채점 기준</summary>

4096−900−800=2396토큰이다. 최근 대화는 2700토큰이므로 304토큰 초과다. 턴 수만 제한하는 정책은 토큰 예산을 보장하지 않는다. 예산 계산 2점, 초과량 2점, 정책의 한계 1점.

</details>

## 9. 누적 입력량

대화 쌍 하나가 100토큰이고 총 5번 호출한다고 가정한다. 현재 질문과 고정 지시문을 제외하고 전체 버퍼가 읽는 과거 기록 토큰의 총합을 계산하라. 최근 2턴 창과 비교하라.

<details><summary>해설과 채점 기준</summary>

전체 버퍼는 0+100+200+300+400=1000토큰이다. 최근 2턴은 0+100+200+200+200=700토큰이다. 이는 단순 길이 모형이며 실제 엔진 캐시나 가격 조건은 포함하지 않는다. 전체 계산 2점, 창 계산 2점, 범위 명시 1점.

</details>

## 10. 요약의 오류 찾기

대화: “행사는 금요일이다.” → “월요일로 바뀌었다.” → “장소는 아직 미정이다.” 요약: “행사는 금요일에 학교에서 열린다.” 어떤 종류의 오류가 있는가? 더 적합한 요약을 작성하라.

<details><summary>해설과 채점 기준</summary>

변경된 최신 날짜를 보존하지 않았고, 원문에 없는 장소를 사실처럼 추가했다. “행사는 금요일에서 월요일로 변경됐으며 장소는 아직 정해지지 않았다”가 적합하다. 최신성·정정 누락 2점, 환각된 장소 1점, 조건을 보존한 요약 2점. 이 문제는 요약이 자연스러운지만 보면 안 된다는 점을 묻는다.

</details>

## 11. 요약 비용의 비교

요약이 80토큰이고 전체 기록이 1000토큰이므로 요약 방식의 총비용은 언제나 92% 싸다는 주장을 평가하라.

<details><summary>해설과 채점 기준</summary>

본 응답 호출이 읽는 기록 길이만 비교한 비율이다. 요약을 만들기 위한 추가 호출의 입력·출력, 갱신 주기, 모델별 비용, 지연, 다른 고정 입력을 고려하지 않았다. 전체 비용이 항상 92% 감소한다고 할 수 없다. 빠진 항목 세 가지 이상 3점, 부분과 전체 구분 2점.

</details>

## 12. 도구 요청과 실제 실행

에이전트가 “검색을 마쳤고 가격은 1200달러입니다”라고 출력했지만 실행기 로그에 검색 호출이 없다. 이를 검색 관찰로 취급해도 되는가? 어떤 로그를 남겨야 하는가?

<details><summary>해설과 채점 기준</summary>

취급하면 안 된다. 모델의 생성 주장과 실제 도구 반환값은 다르다. 도구 이름, 검증된 입력, 실행 여부·상태, 반환값, 출처와 시점 등을 별도로 기록해야 한다. 주장·관찰 구분 2점, 실행 경계 1점, 필요한 로그 2점.

</details>

## 13. 환율 방향 손계산

상품이 1200 USD이고 환율이 0.85 EUR/USD다. EUR 금액을 계산하라. 환율이 반대로 1.20 USD/EUR로 주어졌다면 어떻게 계산하는가?

<details><summary>해설과 채점 기준</summary>

첫 경우는 1200×0.85=1020 EUR다. 둘째는 1200÷1.20=1000 EUR다. 단위를 써서 USD가 약분되는 방향으로 연산한다. 각 계산 2점, 단위 설명 1점. 두 예제는 서로 다른 가정의 환율이며 같은 시점의 동일 환율이라고 가정하지 않는다.

</details>

## 14. 반복 상한과 과제 완료

가격 조회 뒤 계산까지 했지만 최종 종료 상태를 만들기 전에 반복 상한에 도달했다. 프로그램이 오류 없이 끝났다는 이유로 과제 완료로 기록해도 되는가?

<details><summary>해설과 채점 기준</summary>

안 된다. 프로세스 정상 종료와 과제 완료 상태는 다르다. 실행기가 정의한 완료 조건을 충족했는지 확인하고, 미완료라면 현재 확보한 정보와 남은 단계를 표시해야 한다. 이 실습은 명시적 `finish` 단계 전 상한에 도달하면 `incomplete`다. 상태 구분 2점, 완료 계약 2점, 사용자에게 전달할 한계 1점.

</details>

## 15. 학습 도우미의 메모리 설계

학생의 장기 학습 목표, 최근 코드 수정, 정확한 교재 인용을 모두 지원하는 도우미를 설계하라. 모든 정보를 하나의 요약으로만 저장하는 것의 문제와 대안을 설명하라.

<details><summary>해설과 채점 기준</summary>

장기 목표는 출처와 갱신 시점을 갖춘 구조화된 사실 또는 요약으로 유지할 수 있다. 최근 코드 수정은 최근 원문과 현재 코드 상태가 중요하다. 정확한 교재 인용은 원문 근거를 보존하거나 검색해서 확인해야 한다. 요약 하나는 원문 표현을 잃고 오래된 사실·추정을 섞을 수 있다. 요구별 정보 분리 3점, 손실·출처 문제 1점, 근거 접근 대안 1점. 특정 라이브러리 이름보다 설계 이유가 중요하다.

</details>

## 16. 에이전트의 실패를 분해해 평가하기

검색 도구는 오래된 다른 상품 가격을 반환했고, 계산기는 입력값을 정확히 환산했으며, 모델은 출처 없이 현재 가격이라고 답했다. 어느 부분은 성공했고 어느 부분은 실패했는가? 평가 지표 또는 확인 항목 세 개를 제안하라.

<details><summary>해설과 채점 기준</summary>

계산 함수의 산술은 성공했지만 검색 결과의 상품·시점 적합성이 실패했고 최종 응답은 근거와 시점을 과장했다. 확인 항목은 목표 상품 구성 일치, 가격 기준 날짜·통화·세금 조건, 검색 출처, 계산식·환율 방향, 최종 답과 관찰값의 일치 등이다. 구성 요소별 성공·실패 구분 2점, 구체적 확인 항목 세 개 3점. 도구 호출 성공률 하나만으로 전체 정답률을 대신할 수 없다.

</details>
