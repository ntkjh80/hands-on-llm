# 7장 강의 진행안

[전체 목차](../../README.md) · [학습 노트](study.md) · [강의안](lecture.md) · [강의 대본](lecture-script.md) · [시각화](visuals.html) · [실습](lab-guide.md) · [복습 문제](quiz.md)

원문: *Hands-On Large Language Models*, 7장, PDF 물리 페이지 280–315. 총 80분의 수업 설계이며 설명, 질문, 실습, 토론 시간을 포함한다. [강의 대본](lecture-script.md)은 아래 수업 흐름에 따라 교사가 사용할 설명문이다.

## 수업 전 준비

학생은 Python 딕셔너리와 함수, 토큰과 컨텍스트 길이, 기본 프롬프트를 알고 있다고 가정한다. 실제 모델 다운로드나 API 키는 필요 없다. [lab.py](lab.py), [실제 실행 결과](lab-output.txt), [시각화](visuals.html)를 준비한다. GitHub에서 HTML은 소스로 보일 수 있으므로 시각화 파일은 내려받아 브라우저에서 연다. 시각화와 실습에서 사용하는 가격·환율·대화는 교육용 가상 데이터다.

칠판을 세 구역으로 나눈다. 왼쪽에는 ‘현재 모델 입력’, 가운데에는 ‘저장된 상태’, 오른쪽에는 ‘외부 도구’를 적는다. 학생이 혼동할 때마다 지금 설명하는 정보가 어느 칸에 있는지 돌아가 확인한다.

## 수업 전체 흐름

| 시간 | 주제 | 학생이 할 일 | 교사가 확인할 것 |
|---|---|---|---|
| 0–6분 | 기억하는 모델이라는 착각 | 이름을 알려 준 뒤 별도 호출을 상상 | 모델과 애플리케이션 상태를 구별하는가 |
| 6–15분 | 모델 입출력과 양자화 | 40억 가중치의 저장량 계산 | 가중치 크기와 전체 메모리를 구별하는가 |
| 15–25분 | 템플릿과 단일 체인 | 변수와 역할 구분자를 색으로 구별 | 최종 모델 입력을 설명하는가 |
| 25–35분 | 여러 체인 | 단계별 상태 딕셔너리 완성 | 기존 키를 왜 유지해야 하는가 |
| 35–49분 | 전체 버퍼와 최근 창 | 2턴 창을 종이 카드로 이동 | 이름과 나이의 보존 차이를 설명하는가 |
| 49–59분 | 요약 메모리 | 대화에서 요약할 사실을 선택 | 정보 손실과 추가 호출을 인지하는가 |
| 59–69분 | 에이전트와 ReAct | 검색→계산→종료를 역할극 | 요청과 실제 실행을 구별하는가 |
| 69–77분 | 실습·오류 분석 | 실패 조회와 반복 상한 실행 | 성공·불완전 종료를 구별하는가 |
| 77–80분 | 출구 질문 | 세 문장으로 핵심 설명 | 다음 장 검색·RAG로 연결하는가 |

## 0–6분: 모델이 정말 기억하는가

**도입 질문:** “첫 호출에서 내 이름을 알려 주었는데, 두 번째 호출에는 질문만 보냈습니다. 모델은 이름을 어떻게 알 수 있을까요?”

예상 답은 ‘앞의 대화를 기억한다’, ‘같은 프로그램이니 안다’, ‘대화 기록을 넣어야 한다’로 나뉠 수 있다. 교사는 세 번째 답을 출발점으로 삼되 첫 두 답을 바로 틀렸다고 끝내지 않는다. 제품이 과거 대화를 저장할 수 있지만, 그 저장 책임은 애플리케이션에 있으며 현재 호출에 정보를 공급해야 한다는 구조를 설명한다.

**판서:** `현재 출력 = 모델(현재 입력)`와 `현재 입력 = 지시 + 필요한 기록 + 현재 질문`. 이 식은 개념식이며 모델의 모든 구현 세부를 표현하는 수학적 정의는 아니다.

**확인:** “기억 기능을 추가하면 모델 가중치가 매 턴 업데이트되는가?” 기대 답: 아니다. 이 장의 메모리는 과거 내용을 다시 입력에 제공하는 방식이다.

## 6–15분: 파일 형식과 정밀도 구분

[학습 노트 1절](study.md#sec-01)의 모델 로딩 표를 사용한다. GGUF는 형식, FP16은 수치 정밀도라는 두 축을 먼저 판서한다. 원문의 8비트 설명과 실제 FP16 다운로드 코드가 불일치하는 부분을 보여 주고, 설명을 그대로 믿기보다 파일을 확인하는 독해 습관을 강조한다.

**활동 3분:** 가중치가 40억 개일 때 16·8·4비트의 순수 가중치 크기를 계산한다. 십진 GB 기준 답은 8·4·2 GB다. “그러면 필요한 장치 메모리도 정확히 2 GB인가?”를 추가로 묻는다. 학생은 KV 캐시, 활성값, 메타데이터 등을 이유로 아니라고 설명해야 한다.

**판서:** `P × b / 8 bytes`. `max_tokens`와 `n_ctx`를 서로 다른 칸에 적는다. 출력 상한과 전체 컨텍스트 예산을 분리한다.

**오해 점검:** 양자화 수준을 낮추면 항상 더 빠르고 정확도는 변하지 않는다는 주장에는 조건이 빠져 있다. 하드웨어·엔진과 작업별 품질 평가가 필요하다.

## 15–25분: 템플릿을 만들어 보는 활동

**활동지:** `대상은 {audience}입니다. {concept}를 {domain} 예제로 설명하세요.`

학생 두 명이 각각 변수값 세 개를 적는다. 서로 교환해 완성된 프롬프트를 만든다. 그 다음 `audience` 대신 `reader`라는 키를 제공해 보게 한다. 사람은 의미를 짐작해도 프로그램은 필드가 맞아야 한다는 점을 확인한다.

**판서 도식:** `딕셔너리 → 변수 치환 → 채팅 역할 형식 → 모델 → 출력`.

원문 Phi-3의 역할 구분자는 해당 예제의 모델 형식이며 모든 모델에 공통인 문자열이 아니다. 업무 프롬프트 변수와 모델의 채팅 직렬화 형식을 분리해서 설명한다. API가 형식을 처리하는 경우 중복 템플릿을 적용하지 않도록 인터페이스를 확인해야 한다.

**확인 질문:** “모델 답이 비었을 때 사용자 질문만 확인하면 충분한가?” 기대 답: 아니다. 실제로 완성된 입력과 종료 조건·설정·실행 로그를 봐야 한다.

## 25–35분: 세 단계 체인에서 데이터가 사라지지 않게 하기

초기 입력은 `summary='사라진 공책을 찾는 학생'`이라고 둔다. 학생이 아래 표의 빈칸을 채운다.

| 시점 | 보유할 키 |
|---|---|
| 시작 | `summary` |
| 제목 뒤 | `summary`, `title` |
| 인물 뒤 | `summary`, `title`, `character` |
| 이야기 뒤 | `summary`, `title`, `character`, `story` |

**활동:** 일부러 첫 단계가 제목 문자열만 반환하도록 설계한 뒤 둘째 단계가 `summary`를 찾을 때 무엇이 생기는지 설명한다. 정답은 데이터 계약이 맞지 않아 초기 소재를 잃거나 오류가 난다는 것이다. 파이프 기호가 모든 입력을 자동 보존한다는 일반화는 금지한다.

**토론:** 하나의 긴 프롬프트보다 여러 호출이 좋은 이유와 불리한 이유를 각각 두 개 적는다. 기대 답은 중간 결과 활용·검증·재사용, 추가 지연·비용·오류 전파다.

## 35–49분: 대화 창을 종이 카드로 움직이기

다음 네 장의 카드를 쓴다.

1. “내 이름은 민아, 나이는 29세”와 산술 답변.
2. 두 번째 산술 질문과 답변.
3. 이름 질문과 “이름은 민아” 답변.
4. 나이 질문.

두 장만 들어가는 종이 창을 만든다. 3번 호출 직전에 1·2번이 보이고, 4번 호출 직전에 2·3번이 보이게 한다. 학생은 4번 호출에서 이름은 최근 답변에 남을 수 있지만 나이는 남아 있지 않다는 점을 설명한다.

[시각화](visuals.html)에서 창 크기와 호출 위치를 바꾸어 같은 현상을 확인한다. 기록 카드가 원문인지 압축 요약인지도 비교한다.

**판서 계산:** `기록 예산 = 컨텍스트 - 고정 입력 - 출력 예약`. 2048−448−500=1100. 최근 두 턴이 각각 700토큰이면 넘친다. ‘2턴’과 ‘1100토큰’은 다른 종류의 제한이다.

**중간 평가:** “오래된 메시지가 삭제되면 그 정보도 반드시 사라진다”에 찬반을 들게 한다. 정답은 반드시 그렇지는 않다. 정보가 최근 답변에 반복됐을 수 있다.

## 49–59분: 요약은 무엇을 보존해야 하는가

학생에게 다음 대화를 준다. “시험은 금요일이야.” → “월요일로 바뀌었어.” → “나는 수식보다 도식으로 먼저 배우고 싶어.” 각자 30단어 이내로 요약한다. 요약끼리 비교하며 최신 날짜, 정정 관계, 학습 선호가 남았는지 확인한다.

**판서:** `새 요약 = 요약기(이전 요약 + 새 대화)`. 응답 호출과 요약 호출을 서로 다른 화살표로 표시한다. 요약이 짧다는 이유만으로 전체 비용이 반드시 낮다고 결론 내리지 않는다.

원문 예제에서 모델이 말한 잘못된 시스템 설명도 다음 요약에 들어간다는 사례를 다룬다. 사용자 발언, 도구 관찰, 모델 추정의 출처가 다른데 요약에서 같은 사실처럼 합쳐질 수 있음을 설명한다.

**확인 질문:** “요약만 보고 최초 질문을 따옴표로 정확히 인용해도 되는가?” 기대 답: 정확한 원문이 남았다는 근거가 없다면 안 된다. 주제의 재서술과 원문 인용을 구별해야 한다.

## 59–69분: ReAct 역할극

세 학생에게 각각 ‘행동 선택자’, ‘실행기’, ‘도구’ 역할을 준다. 사용자 요청은 가상 상품 가격을 USD에서 EUR로 바꾸는 것이다. 가격은 1200 USD, 교육용 환율은 0.85 EUR/USD다.

1. 선택자는 가격 조회 요청을 작성한다.
2. 실행기는 허용 도구와 입력을 확인하고 조회 도구에 전달한다.
3. 도구는 가격·통화·출처를 반환한다.
4. 선택자는 관찰을 보고 환산 계산을 요청한다.
5. 실행기는 계산을 수행하고 결과 1020 EUR를 돌려준다.
6. 선택자는 출처와 사용 환율을 포함해 종료한다.

**핵심 질문:** “선택자가 ‘검색했다’고 말했지만 도구 역할 학생이 요청을 받지 않았다면 검색 결과가 있는가?” 기대 답: 없다. 모델의 주장과 실제 도구 관찰은 다르다.

**변형:** 조회 도구가 오류를 반환한다. 선택자가 다른 질의를 시도할지, 조건을 물을지, 종료할지 결정한다. 실행기는 반복 상한을 유지한다.

## 69–77분: CPU 실습과 실패 사례

[실습 안내](lab-guide.md)에 따라 기본 실행, `--lookup-fail-first`, `--max-steps 1`을 비교한다. 첫째는 정상 완료, 둘째는 한 번의 조회 실패 후 다른 조회 경로, 셋째는 미완료 종료를 보여 준다. 이 정책은 규칙형이고 실제 LLM의 도구 선택 능력을 측정하지 않는다고 반드시 설명한다.

학생은 실습에서 발견한 오류를 네 범주 중 하나로 분류한다: 입력·출력 키 오류, 정보 보존 오류, 도구 실행 오류, 결과 해석 오류. 한 범주를 고른 뒤 수정할 위치를 말하게 한다.

## 77–80분: 출구 질문

다음 세 문장을 학생 자신의 말로 완성한다.

- “이 장의 메모리는 학습과 다르다. 왜냐하면 …”
- “요약이 짧더라도 전체 비용을 계산할 때 …”
- “도구가 정확한 계산을 했더라도 최종 답이 틀릴 수 있다. 예를 들면 …”

각 문장에 구조적 이유와 구체적인 예가 있으면 통과다. 다음 8장은 검색 결과를 단순히 받는 단계를 넘어, 좋은 근거를 찾고 순위를 매기고 평가하는 방법으로 연결된다고 마무리한다.
