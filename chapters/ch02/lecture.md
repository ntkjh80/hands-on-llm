## 0–6분 도입과 진단

판서에 세 표현을 적는다.

```text
"나는 배를 탔다"
[17, 42, 9]
[[0.2, -0.4], [0.7, 0.1], [-0.1, 0.6]]
```

숫자는 가상 값이라고 먼저 말한다. “어느 표현이 사용자의 문장이고, 어느 것이 사전의 번호이고, 어느 것이 모델 계산에 쓰는 좌표인가?”를 묻는다. 학생이 번호 42에 더 큰 의미가 있다고 말하면 학번 비유를 사용한다. 학번과 성향 벡터를 구분하되, 실제 임베딩 차원에 사람이 이름을 붙여놓는 것은 아니라고 바로 한계를 설명한다.

**교사 설명 포인트:** 토큰화는 단위를 정하고 번호를 붙이는 일이다. 임베딩은 그 단위를 학습 가능한 수치 표현으로 바꾸는 일이다. 일반적인 생성 모델은 다음 토큰을 반복해 고른다.

**기대 답:** 두 번째는 ID 배열이고, 세 번째는 각 ID에 대응한 벡터의 배열이다. ID의 숫자 크기로 의미적 유사도를 판단할 수 없다.

## 6–18분 단위가 바뀌면 어떤 일이 생기는가

### 활동 A 분할 전에 예측하기

`A가😊`, `playing`, `    return value`, `870 871`을 보여준다. 학생은 다음 세 항목을 적는다.

1. 글자나 바이트를 단위로 할 때 예상 길이.
2. 단어 전체를 어휘에 넣었을 때 새 표현을 처리하는 방법.
3. 공백과 대소문자를 지우면 사라지는 정보.

[시각 실험](visuals.html)의 첫 패널에서 입력을 바꾸며 예측을 확인한다. 이 도구의 서브워드 모드는 교육용 고정 조각 분할이며 실제 BPE 체크포인트 출력이 아니라는 점을 확인한다.

**판서:** `A가😊`는 코드 포인트 3개, UTF-8 바이트 8개다. 바이트 분할과 문자 분할은 다르다. 이모지 한 조각을 디코딩한 깨진 표시는 전체 복원이 불가능하다는 증거가 아니다.

### 활동 B 컨텍스트 예산

가상의 토큰 예산을 12로 놓는다. `playing` 세 번을 문자·단어·`play + ing`으로 각각 표현하면 몇 단위를 쓰는지 계산한다. 공백을 별도 처리하는 경우와 단어에 붙이는 경우가 있어 정확한 수는 규약에 따라 달라진다고 설명한다. 목표는 임의의 숫자를 외우는 것이 아니라 **단위가 작아질수록 시퀀스가 길어질 수 있음**을 이해하는 것이다.

**예상 오답:** “서브워드는 언제나 미지의 단어를 처리하므로 `[UNK]`가 없다.”

**교정:** 필요한 문자나 바이트 fallback이 있어야 한다. 서브워드라는 이름만으로 모든 문자를 표현할 수 있는 것은 아니다.

## 18–28분 모델 비교를 설계 문제로 읽기

세 그룹에 다음 사례를 맡긴다. 각 그룹은 “보존되는 정보, 잃는 정보, 토큰 수의 영향”을 한 문장씩 발표한다.

| 사례 | 질문 | 기대 답 |
|---|---|---|
| BERT uncased와 cased | `Apple`과 `apple`을 합치면 무엇이 달라지는가? | 중복은 줄지만 대문자 의미가 사라질 수 있음 |
| GPT-2의 바이트 조각 | 개별 토큰의 `�`는 `[UNK]`와 같은가? | 전체 조각으로 복원 가능하면 정보 손실과 다름 |
| 코드용 토크나이저 | 네 칸 들여쓰기와 파일 경계가 왜 중요한가? | 코드 구조와 컨텍스트를 표현하는 단위이기 때문 |

**판서할 세 축:** `알고리즘 / 매개변수·정규화·특수 토큰 / 학습 데이터 영역`.

SentencePiece는 도구 체계이고 내부 알고리즘과 구분해 읽는다고 정리한다. Phi-3의 대화 역할 토큰, Galactica의 인용 표지, StarCoder2의 파일·저장소 표지는 같은 설계 질문의 다른 답이다. 모든 모델의 어휘 크기를 암기시키지 않는다.

**확인 질문:** 같은 BPE와 같은 어휘 크기를 쓰면 결과도 같은가? 학습 데이터와 정책이 다르면 달라진다.

## 28–40분 행렬 lookup과 차원 읽기

가상의 어휘 크기 `V=6`, 차원 `d=3`인 표를 판서한다. ID `[1,4,1]`에 해당하는 행을 색연필로 표시하게 한다. 같은 ID가 두 번 나오면 초기 벡터도 두 번 같은지 확인한다.

**손계산 과제:** `V=32,000`, `d=384`, 값 하나 4바이트라면 임베딩 행렬의 원소 수와 저장량을 구한다. 정답은 12,288,000개, 49,152,000바이트다. 전체 모델 메모리라고 답하면 다른 층과 학습 상태가 빠졌음을 짚는다.

원문의 `[1,4,384]`를 적고 각 축 아래에 `배치`, `토큰 위치`, `벡터 차원`을 쓴다. `Hello world`인데 위치가 4개인 이유를 학생에게 추론하게 한다. `[CLS]`와 `[SEP]`를 보여주고 특수 토큰도 위치를 차지한다고 연결한다.

**오류 찾기 미니 활동:** 모델과 다른 토크나이저를 사용했지만 어휘 크기가 같다면 괜찮은가? 아니다. 행 번호의 의미가 달라질 수 있다. 원문 DeBERTa 예제의 서로 다른 체크포인트 이름을 호환성 검토 사례로 사용한다.

## 40–51분 문맥과 풀링

“배를 먹었다”, “배를 탔다”를 판서한다. 학생에게 `배`의 시작 벡터와 최종 벡터가 각각 같아야 하는지 묻는다. 같은 ID라면 lookup은 같지만, 모델을 통과한 문맥 벡터는 달라질 수 있다.

**교사 설명 포인트:** 문맥 벡터는 등장 위치의 표현이다. 문장 임베딩은 텍스트 전체의 표현이다. 토큰 벡터를 평균내는 것은 하나의 집계 방법이며 학습 목적까지 대신하지 않는다.

### 손계산과 확인

```text
h1=[2,0], h2=[0,2], padding=[10,10]
mask=[1,1,0]
```

학생은 마스크 평균 `[1,1]`과 무조건 평균 `[4,4]`를 계산한다. [시각 실험](visuals.html)에서 패딩 제외를 끄고 켜며 점이 어떻게 움직이는지 본다. 이어서 `[1,0]`과 `[1,1]`의 코사인이 약 0.707임을 계산한다.

**기대 설명:** 점수 0.707은 정답 확률이나 의미 일치 비율이 아니다. 특정 표현 공간의 방향 유사도다.

## 51–66분 관측에서 학습 신호 만들기

종이에 다섯 항목 `A B C D E`를 적는다. 중심 C, 창 크기 2의 양성 쌍 네 개를 쓰게 한다. 다음으로 중심 A에서 몇 개가 생기는지 묻는다. 경계에서는 두 개가 생긴다. 이 차이를 실제 반복문의 인덱스 범위와 연결한다.

양성만 있으면 모든 쌍을 참이라고 말하는 모델이 성공해 보일 수 있음을 설명한다. 잡음 항목 F를 추가해 `(C,F,0)`을 만든다. 단, F가 실제로 아무 관계도 없다는 진리 판정은 아니라고 강조한다.

**판서:** `s=u·v`, `p=sigmoid(s)`, `gradient=p-y`.

`u=[1,0]`, `v=[0,1]`, `y=1`, `η=0.1`에서 업데이트 후 `[1,0.05]`, `[0.05,1]`을 계산한다. 시각 실험의 양성·음성 선택을 바꾸어 내적의 방향을 비교한다. 이진 판별 점수와 어휘 전체에 대한 softmax 확률은 다르다고 짚는다.

**확인 질문:** 왜 업데이트하기 전 u와 v를 모두 저장해야 하는가? 같은 상태에서 계산한 경사를 동시에 적용하기 위해서다.

## 66–79분 음악 추천 실습

프로젝트 루트에서 다음을 실행한다.

```bash
python3 chapters/ch02/lab.py
```

학생은 실행 전에 “학습에 제목과 장르가 들어갈까?”를 예측한다. 정답은 아니다. 코드에서 가상 재생목록의 ID만 학습에 쓰이고 제목·장르는 표시용이다. 실제 음원이나 저자 데이터의 재현이 아님을 확인한다.

기본 설정에서는 고정 학습 쌍의 평균 손실이 약 0.6944에서 0.2776으로 내려가고 같은 가상 그룹의 곡들이 가까운 결과로 나타난다. 이 수치는 [저장된 실제 출력](lab-output.txt)과 비교한다. 학습 쌍에 대한 손실 감소를 실제 사용자 만족도 개선이라고 쓰지 않게 한다.

### 짝 토론

- 한 번도 보지 않은 새 곡 ID가 들어오면 무엇이 필요한가?
- 같은 재생목록을 복사하여 평가 데이터에 넣으면 어떤 문제가 생기는가?
- `window`를 크게 하면 어떤 관계를 더 배우게 되는가?
- 곡 ID와 데이터프레임 행 번호가 다를 때 `iloc`로 조회하면 무엇이 잘못될 수 있는가?

원문의 `Word2Vec(...)` 생성자와 skip-gram 설명의 연결에서는 `sg` 설정을 확인해야 한다는 점만 짧게 설명한다. API 옵션 암기보다 명시적 설정과 입력·출력 점검의 습관을 강조한다.
