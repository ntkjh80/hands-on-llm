## 1. 토큰 ID는 의미 좌표인가

어휘표에서 `cat=10`, `dog=11`, `river=900`이다. “cat과 dog의 번호 차이가 작으므로 의미가 비슷하다”는 주장을 평가하라.

<details><summary>정답과 채점 기준</summary>

ID는 항목을 찾는 정수 이름표다. 숫자 차이는 의미 거리로 학습된 것이 아니다. 의미적 관계는 해당 ID에 연결된 임베딩과 적절한 유사도 계산으로 살펴야 한다. 우연히 비슷한 단어의 ID가 이웃할 수는 있지만 그 사실만으로 근거가 되지 않는다.

**5점:** 이름표의 성격 2점, 번호 차이가 의미를 보장하지 않는 이유 2점, 임베딩과 구별 1점.

</details>

## 2. 새 단어와 `[UNK]`

단어 토크나이저가 새 회사 이름 두 개를 모두 `[UNK]`로 바꿨다. 서브워드 토크나이저로 바꾸면 문제가 항상 해결되는가?

<details><summary>정답과 채점 기준</summary>

항상은 아니다. 서브워드는 작은 조각으로 새 단어를 조합할 수 있지만 필요한 문자나 바이트 fallback이 있어야 한다. 그렇지 않으면 여전히 unknown이 생길 수 있다. 이미 서로 다른 입력을 하나의 `[UNK]`로 합쳤다면 그 ID만으로 원래 두 이름을 구별할 수 없다.

**5점:** 서브워드의 조합 장점 1점, 기본 구성 요소 조건 2점, 정보 손실 설명 2점.

</details>

## 3. 문자와 바이트 손계산

UTF-8에서 `A`는 1바이트, `가`는 3바이트, `😊`는 4바이트다. `A가😊`의 코드 포인트 수와 바이트 수를 구하고, 이것을 실제 LLM 토큰 수라고 말할 수 있는지 설명하라.

<details><summary>정답과 채점 기준</summary>

코드 포인트는 3개, 바이트는 8개다. 실제 토큰 수는 선택한 토크나이저의 어휘와 분할 규칙에 따라 달라진다. 바이트 기반 서브워드도 여러 바이트를 합친 조각을 사용할 수 있으므로 8개라고 단정할 수 없다.

**5점:** 3개 1점, 8바이트 1점, 토크나이저 의존성 2점, 바이트 기반 서브워드 구별 1점.

</details>

## 4. 깨진 문자와 정보 손실

한 이모지가 세 토큰으로 인코딩되었다. 각 ID를 따로 디코딩하면 `�`가 보이지만 세 ID를 함께 디코딩하면 원래 이모지가 나온다. `[UNK]`와 어떤 차이가 있는가?

<details><summary>정답과 채점 기준</summary>

바이트 조각 하나는 완전한 문자 인코딩이 아닐 수 있다. 전체 조각이 보존되어 있으면 합쳐서 복원할 수 있다. 반면 여러 미지의 입력이 같은 `[UNK]`로 바뀌었다면 구별 정보가 사라질 수 있다. 개별 표시 결과만 보고 정보 소실을 판단하면 안 된다.

**5점:** 조각 디코딩의 불완전성 2점, 전체 복원 가능성 1점, `[UNK]`와의 차이 2점.

</details>

## 5. 토크나이저 비교 실험 설계

한국어 고객 상담과 Python 코드 검색을 하나의 모델로 처리하려 한다. 후보 토크나이저 둘을 비교할 최소 실험을 설계하라. 토큰 수 외에 적어도 세 가지를 확인하라.

<details><summary>모범 설계와 채점 기준</summary>

한국어 조사·전문 용어·고유명사, 코드의 들여쓰기·줄바꿈·대소문자·숫자가 포함된 대표 입력을 준비한다. 토큰 수 분포와 unknown 발생을 기록하고, encode-decode 뒤 원문 구분이 보존되는지 확인한다. 특히 `User/user`, 네 칸 공백, 줄바꿈, 한국어 새 상품명을 비교한다. 이후 실제 작업의 검색·분류 성능과 처리 비용을 함께 본다. 가장 짧은 토큰 수만으로 선택하지 않는다.

**5점:** 두 영역을 반영한 데이터 1점, 세 가지 이상 보존성 점검 2점, 작업 성능·비용 연결 1점, 단일 지표 한계 1점.

</details>

## 6. 임베딩 행렬의 크기

어휘 크기 30,000, 차원 128, 값 하나 4바이트인 입력 임베딩 행렬의 원소 수와 저장량을 계산하라. 입력 `[1,7,1,9]`의 lookup 출력 모양도 쓰라.

<details><summary>풀이와 채점 기준</summary>

원소 수는 `30,000×128=3,840,000`, 저장량은 `15,360,000바이트`, 십진 MB로 15.36MB다. 배치 축을 빼면 lookup 출력은 `[4,128]`, 배치 한 개로 표현하면 `[1,4,128]`이다. 같은 ID 1은 초기 lookup에서 같은 행을 두 번 사용한다. 이 값은 모델 전체 메모리가 아니다.

**5점:** 원소 수 1점, 바이트 1점, 출력 모양 2점, 전체 메모리와 구분 1점.

</details>

## 7. 출력 모양 해석

토큰화 후 문장 세 개가 각각 패딩을 포함해 길이 12가 되었고 모델의 은닉 차원은 384다. 토큰별 출력과 평균 풀링 후 출력의 모양을 쓰라.

<details><summary>정답과 채점 기준</summary>

토큰별 출력은 `[3,12,384]`, 문장별 평균 풀링 후에는 `[3,384]`다. 풀링은 토큰 위치 축을 합치며 벡터 차원은 유지한다. 패딩 마스크를 반영해야 하고, 특수 토큰 포함 여부는 모델의 설계에 맞춰 정한다.

**5점:** 두 모양 각 2점, 패딩 처리 1점.

</details>

## 8. 정적 벡터와 문맥 벡터

“배를 먹었다”와 “배를 탔다”의 `배`가 같은 토큰 ID다. 모델의 입력 임베딩은 같은가? 모델의 마지막 층 출력도 반드시 같은가?

<details><summary>정답과 채점 기준</summary>

같은 입력 임베딩 행렬에서 같은 ID를 lookup하면 정적 벡터는 같다. 이후 다른 토큰·위치와 상호작용하므로 문맥 벡터는 달라질 수 있다. 구조상 구별 가능하다는 것과 모든 중의성을 항상 정확히 해결한다는 것은 다르다.

**5점:** lookup 동일 2점, 문맥 출력 차이 2점, 성능 보장과 구분 1점.

</details>

## 9. 마스크 평균 디버깅

벡터가 `[2,0]`, `[0,2]`, `[10,10]`, 마스크가 `[1,1,0]`이다. 올바른 평균과 무조건 평균을 계산하라. 패딩 벡터가 `[0,0]`이면 마스크를 생략해도 항상 괜찮은가?

<details><summary>풀이와 채점 기준</summary>

올바른 평균은 `[1,1]`, 무조건 평균은 `[4,4]`다. 패딩이 0이어도 세 위치로 나누면 `[2/3,2/3]`가 되어 크기가 달라진다. 이 예에서는 방향이 같아 코사인에 영향을 주지 않을 수도 있지만 모든 후속 연산이 크기를 무시하는 것은 아니다. 따라서 일반적으로 생략해도 된다고 말할 수 없다.

**5점:** 두 계산 각 1점, 0 패딩의 분모 문제 2점, 후속 연산 조건 1점.

</details>

## 10. 코사인 유사도 손계산

`u=[1,0]`, `v=[1,1]`, `w=[2,0]`이다. `cos(u,v)`와 `cos(u,w)`를 구하고, 0.8이라는 코사인 점수의 올바른 해석을 설명하라.

<details><summary>풀이와 채점 기준</summary>

`cos(u,v)=1/√2≈0.7071`, `cos(u,w)=2/(1×2)=1`이다. 코사인은 길이를 정규화한 방향 유사도다. 0.8은 정답 확률 80%나 뜻의 일치 비율 80%가 아니다. 모델·데이터·과제 안의 비교 점수이며 임계값은 검증해야 한다.

**5점:** 두 계산 각 1점, 방향과 크기 구별 1점, 확률 해석 오류 2점.

</details>

## 11. 슬라이딩 윈도우 쌍의 수

서로 다른 항목 네 개 `A B C D`와 창 크기 2가 있다. 중심별 이웃을 적고 방향 있는 양성 쌍의 총수를 구하라. 창 크기 1이면 몇 개인가?

<details><summary>풀이와 채점 기준</summary>

창 2에서 A는 B,C 두 개, B는 A,C,D 세 개, C는 A,B,D 세 개, D는 B,C 두 개로 총 10개다. `(A,B)`와 `(B,A)`는 중심 역할이 달라 별도 예제다. 창 1에서는 1+2+2+1=6개다. 경계에서 이웃 수가 줄어든다는 점이 핵심이다.

**5점:** 중심별 2·3·3·2 2점, 총 10개 1점, 방향 구별 1점, 창1의 6개 1점.

</details>

## 12. 음성 예제는 진짜 무관한가

한 쌍이 말뭉치에서 관측되어 양성이 되었다. 같은 중심과 관련된 다른 단어가 무작위 음성으로 뽑힐 수 있는가? 왜 양성만으로 학습하지 않는가?

<details><summary>정답과 채점 기준</summary>

관련된 단어가 음성으로 뽑히는 false negative가 생길 수 있다. 무작위 추출은 전 세계적 무관함을 판정하는 절차가 아니다. 양성만 있으면 모든 쌍을 양성이라고 출력하는 쉬운 해법이 생기므로 구별을 위한 잡음 예제를 넣는다. 샘플링 분포와 라벨 구성은 학습된 관계에 영향을 준다.

**5점:** false negative 가능성 2점, 양성만의 자명한 해법 2점, 샘플링 영향 1점.

</details>

## 13. 경사 한 번 계산

`u=[1,0]`, `v=[0,1]`, `y=0`, `η=0.1`이다. `p=sigmoid(u·v)`, `g=p-y`를 이용해 두 벡터를 동시에 한 번 업데이트하라.

<details><summary>풀이와 채점 기준</summary>

내적 0, p=0.5, g=0.5다. `u_new=u-0.1×0.5×v=[1,-0.05]`, `v_new=v-0.1×0.5×u=[-0.05,1]`이다. 내적은 -0.1, sigmoid는 약 0.4750이다. 음성 쌍의 점수가 내려간다. 두 식 모두 업데이트 전 벡터를 사용한다.

**5점:** p와 g 1점, 두 벡터 각 1점, 내적·점수 방향 1점, 동시 업데이트 1점.

</details>

## 14. 구현의 조용한 불일치

학습 설명에서는 skip-gram이라고 했지만 Gensim `Word2Vec`를 생성할 때 `sg`를 지정하지 않았다. 또 토크나이저는 모델 A, 가중치는 모델 B에서 읽었다. 어떤 확인이 필요한가?

<details><summary>정답과 채점 기준</summary>

사용 라이브러리의 기본값과 실제 모델 설정을 확인한다. Gensim 문서의 `sg=0`은 CBOW이며 skip-gram을 의도하면 `sg=1`을 명시한다. 토크나이저와 모델은 어휘 크기뿐 아니라 ID 대응·특수 토큰·전처리 호환성을 확인해야 한다. 보통 같은 체크포인트를 사용하는 것이 출발점이다. 코드가 에러 없이 돌아간다고 의미적 호환성이 보장되지는 않는다.

**5점:** 학습 방식 설정 2점, ID 대응과 호환성 2점, 실행 성공과 올바른 의미 구분 1점.

</details>

## 15. 추천 조회 디버깅

곡 정보의 인덱스는 문자열 ID `'10'`, `'2172'`, `'42'` 순서다. ID `'2172'`의 곡을 `iloc[2172]`로 찾으려 한다. 문제와 수정 방향을 설명하라.

<details><summary>정답과 채점 기준</summary>

`iloc`는 행 위치를 사용하므로 2,172번째 위치를 찾으려 한다. ID 라벨 `'2172'`와 다른 개념이며 여기서는 범위를 넘는다. 인덱스 라벨 조회는 `loc['2172']`를 사용한다. 모델의 곡 ID와 메타데이터 인덱스 타입도 문자열로 일관되게 유지한다. 추천 ID 리스트의 순서와 결과 행 순서도 확인한다.

**5점:** 위치와 라벨 구별 2점, 수정 예 1점, 타입 1점, 순서 점검 1점.

</details>

## 16. 추천 평가 설계

가상 실습의 손실이 0.6944에서 0.2776으로 줄고 같은 그룹의 곡들이 추천되었다. “실제 추천 품질이 검증되었다”는 보고서를 어떻게 고칠 것인가? 추가 평가 두 가지를 제안하라.

<details><summary>모범 답안과 채점 기준</summary>

“설계한 가상 재생목록의 고정 학습 쌍에서 손실이 줄고 공동 출현 그룹이 벡터 이웃으로 나타났다”로 범위를 좁힌다. 실제 추천 품질을 검증하려면 보지 않은 재생목록이나 시간 이후의 소비 항목으로 평가하고, 인기 기반 기준선과 비교할 수 있다. 사용자·목록 복사본의 누출을 방지하고 희귀 곡·신규 곡도 별도로 점검한다. 단순 학습 손실은 일반화나 사용자 만족도를 대신하지 않는다.

**5점:** 보고 범위 수정 2점, 평가 두 가지 각 1점, 누출 또는 기준선 고려 1점.

</details>

## 17. 새 노래와 개인화 설계

새 곡이 아직 어떤 재생목록에도 없다. ID 임베딩 기반 추천 시스템은 무엇을 모르며, 어떤 추가 경로를 설계할 수 있는가? 곡 하나의 이웃 검색이 개인화 추천과 같은지도 설명하라.

<details><summary>모범 답안과 채점 기준</summary>

새 ID는 학습된 관계 벡터가 없을 수 있다. 제목·설명·가사·오디오 특징 등 콘텐츠 기반 표현이나 인기·신규 항목 정책을 대체 경로로 붙일 수 있다. 이는 추가 설계이며 기존 ID 모델이 자동으로 아는 것이 아니다. 항목 하나의 이웃 검색에는 사용자별 선호가 명시적으로 들어가지 않으므로 개인화와 동일하지 않다. 최근 청취나 여러 취향을 어떻게 표현할지도 정해야 한다.

**5점:** cold start 원인 2점, 추가 경로와 범위 1점, 개인화 구별 2점.

</details>

## 18. 긴 문서와 평균의 한계

한 벡터의 차원이 항상 768이면 아무 길이의 문서도 정보 손실 없이 담을 수 있다는 주장을 반박하라. 검색 용도로 어떤 후속 설계를 고려할 수 있는가?

<details><summary>모범 답안과 채점 기준</summary>

고정된 출력 차원은 입력 길이 제한이 없다는 뜻이 아니다. 모델의 토큰 한도를 넘으면 잘리거나 나누어 처리해야 한다. 여러 주제를 한 벡터로 평균내면 세부 정보가 희석될 수 있고, 임베딩은 원문 전체를 무손실 압축한 저장소가 아니다. 검색에서는 의미 단위 청킹, 조각별 벡터, 문서 메타데이터, 후속 재정렬 등으로 관련 부분을 찾는 설계를 고려할 수 있다.

**5점:** 입력 한도 2점, 정보 희석·무손실 오해 2점, 후속 설계 1점.

</details>
