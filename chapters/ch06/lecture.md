# 6장 프롬프트 엔지니어링 강의안

[전체 목차](../../README.md) · [학습 노트](study.md) · [강의안](lecture.md) · [강의 대본](lecture-script.md) · [시각화](visuals.html) · [실습 안내](lab-guide.md) · [복습 문제](quiz.md)

**수업 설계**: 85분. 설명, 손계산, 조작, 토론을 포함한 시간이며 대본만 읽는 데 걸리는 시간이 아니다. Python의 리스트·딕셔너리와 기초 확률을 아는 학습자를 대상으로 한다. 원문 범위는 *Hands-On Large Language Models*, Chapter 6, PDF 물리 페이지 236–279다.

## 수업 후 보여 줄 수 있어야 할 능력

- 요청을 지시·자료·출력 계약으로 바꾸고 모호한 기준을 찾아낸다.
- 온도와 top-p의 효과를 수치로 구별한다.
- 예시 제공, 프롬프트 연결, CoT, self-consistency, ToT의 차이를 설명한다.
- JSON 파싱과 스키마·근거 검증을 분리한다.
- 자신의 결과가 실제 모델 실험인지 교육용 모형 계산인지 명확하게 표시한다.

## 준비물

교사는 [학습 노트](study.md)와 [강의 대본](lecture-script.md)을 읽고 [시각화](visuals.html)를 브라우저에서 연다. 학습자는 종이 또는 메모 도구, Python 3 실행 환경을 준비한다. 모델 다운로드, GPU, API 키는 이 수업에 필요하지 않다. 수업 중 계산 결과는 [실제 실행 출력](lab-output.txt)과 비교한다. 원문의 실제 모델 예제는 개념과 코드의 역할을 설명하는 수준으로 다룬다.

## 1교시 도입 0–6분

### 판서

```text
좋은 프롬프트 = 원하는 결과를 확인할 수 있게 만드는 입력
시스템의 네 부분 = 모델 / 입력 / 선택 규칙 / 검증
```

제시할 요청은 “이 문의를 적절히 처리해 줘”다. 문의는 “같은 상품이 두 번 결제되었고 배송은 아직 시작되지 않았습니다”로 둔다. 학습자에게 이 요청에서 결정되지 않은 세 가지를 찾게 한다. 작업이 분류인지 답장인지 환불인지, 결과 형식이 무엇인지, 결제와 배송 중 우선 범주를 무엇으로 정할지 등이 기대 답이다.

교사는 실제 환불 같은 외부 조치와 학습용 분류를 구분한 뒤 오늘의 과제를 분류 결과 생성으로 좁힌다. 이 활동의 목표는 모호한 요구를 모델의 능력 문제와 구분하는 것이다.

## 2교시 모델과 템플릿 6–14분

### 설명 자료

[학습 노트 1.1–1.2](study.md#sec-02)의 표를 사용한다. Phi-3-mini는 원문 당시의 실습 선택이며 최신 모델 추천으로 설명하지 않는다. 3.8B × 2바이트 = 약 7.6GB는 가중치만의 거친 계산이다. 캐시와 실행 버퍼를 추가하면 실제 요구량이 달라진다.

### 미니 활동

아래 세 메시지를 역할에 배치하게 한다.

1. “색깔이 red이면 warm, blue이면 cool로 분류한다. 입력: red”
2. “warm”
3. “입력: blue”

기대 배열은 user, assistant, user다. 이어서 이것이 토크나이저의 chat template를 통해 모델이 읽는 토큰열로 바뀐다고 설명한다. 모든 예시를 한 문자열에 넣을 수도 있지만, 사용할 모델이 기대하는 형식과 역할 경계를 명확히 해야 한다.

**확인 질문**: `return_full_text=False`는 모델의 추론 능력을 올리는가? 아니다. 반환 결과에서 프롬프트를 포함할지에 관한 후처리 성격의 설정이다.

## 3교시 토큰 선택 14–28분

### 손계산 카드

```text
토큰 A   B   C   D
확률 .64 .24 .09 .03
top-p = .80
```

2분 동안 남을 후보와 재정규화 값을 계산하게 한다. A만으로 0.8에 못 미치므로 A와 B를 남긴다. 합 0.88로 나누면 약 0.727과 0.273이다. 이 카드는 반올림한 확률이므로 실제 로짓 실습의 0.731과 0.269와 조금 다르다는 점을 설명한다.

### 시각화 조작

[토큰 선택 실험](visuals.html#sampling)을 기본 설정으로 연다. T를 0.5, 1, 2로 바꿀 때 학습자가 먼저 가장 큰 확률과 후보 개수의 방향을 예상하게 한다. 이어 top-k=1로 바꾸고 T를 움직인다. 최종 확률이 A=100%로 유지되지만 온도 적용 분포는 계속 바뀌는 것을 확인한다.

### 반드시 짚을 오해

- 온도는 모델의 지식을 추가하지 않는다.
- top-p=0.8은 개별 확률이 0.8 이상인 후보만 남기는 규칙이 아니다.
- 높은 온도에서 매번 반드시 다른 답이 나오는 것은 아니다.
- 온도 0은 softmax 수식에 직접 대입하는 정상 입력이 아니다.
- 길이 상한이 있으면 JSON이 도중에 잘릴 수 있다.

## 4교시 모듈과 예시 28–39분

일곱 구성 요소를 모두 써 보는 것보다 어떤 오류에 어떤 요소가 필요한지 판단하게 한다. 처음에는 지시·자료·형식만 제시하고, 독자가 초보자라는 조건을 추가했을 때 어떤 부분이 바뀌어야 하는지 묻는다. 기대 답은 용어 정의와 설명 깊이이며, 정답 자체를 바꾸면 안 된다.

### 짝 활동

문의 분류 범주는 billing, delivery, product다. 한 팀은 zero-shot 지시를 작성하고 다른 팀은 두 개의 예시를 더한다. 예시가 모두 billing이면 무엇이 빠졌는지 토론한다. 혼합 문의 우선순위와 드문 범주가 빠질 수 있다. 예시의 개수와 범주 다양성을 구별한다.

### 판서

```text
shot = 시범 입력 + 대응하는 정답
현재 질문은 시범 개수에 넣지 않는다.
문맥 내 학습: 입력 조건 변화
미세 조정: 모델 파라미터 업데이트
```

실제 모델을 이 시간에 실행하지 않으므로 어느 프롬프트가 더 높은 정확도인지 결론내리지 않는다. 여기서는 설계의 명확성과 검증 가능성을 평가한다.

## 5교시 프롬프트 연결 39–49분

제품 이름·슬로건·판매 문구 과제를 세 단계로 분해한다. 첫 단계에서 “방수”라는 가짜 기능이 생겼다고 가정한다. 다음 단계에 첫 출력만 넘겼을 때 어떤 오류가 생기는지 질문한다. 기대 답은 근거 없는 기능이 확정 사실처럼 확장된다는 것이다.

학습자는 각 단계의 입력과 출력 필드를 적는다. 이름 단계는 확정된 특징과 후보 이름, 슬로건 단계는 확정 특징과 선택된 이름, 판매 문구 단계는 동일 원본 특징과 선택 결과를 받게 한다. 각 단계의 출력 길이와 무작위성을 다르게 설계할 수 있다는 점도 짚는다.

검증은 문구가 예쁜지뿐 아니라 실제 사양에 없는 주장이 들어갔는지 확인해야 한다. 원문 그림은 세 단계, 코드 예시는 이름·슬로건을 합친 두 호출이라는 차이도 알려 준다.

## 6교시 풀이·투표·탐색 49–62분

### 판서

| 전략 | 추가 계산의 위치 |
|---|---|
| CoT | 하나의 답변 안의 중간 풀이 |
| Self-consistency | 여러 완성된 답변의 마지막 답 비교 |
| ToT | 중간 후보 생성·평가·가지치기 |

연필 14자루에 3상자×4자루를 더하고 5자루를 나누어 주는 문제를 사용한다. 답은 21이다. 긴 설명 자체를 채점하지 말고 식, 단위, 최종 결과를 확인한다.

투표 후보로 `21`, `21자루`, `20`, `21`, `22`를 제시한다. 문자열을 그대로 세면 왜 문제가 되는지 묻는다. 정규화 후 21이 3표라는 것을 확인한다. 이어 [다수결 실험](visuals.html#voting)에서 q=0.7, n=5의 독립과 완전 상관을 비교한다. 실제 모델의 정답률이 83.7%라고 말하지 않도록 주의한다.

마지막으로 상태 1에서 +3 또는 ×2를 최대 세 번 사용해 10을 만드는 탐색을 제시한다. 폭 1이면 1→4→8→11로 실패하고, 폭 2면 7을 보존하여 10에 도달한다. 중간 평가 기준이 완벽하지 않다는 점을 보여 주는 활동이다.

## 7교시 출력 검증 62–76분

### 오류 분류 카드

| 출력 상황 | 첫 실패 지점 |
|---|---|
| 닫는 중괄호가 없음 | 파싱 |
| priority가 문자열 “2” | 스키마 |
| label이 허용되지 않은 other | 스키마 |
| evidence가 입력에 없는 “환불 완료” | 근거 검사 |
| 모든 검사 통과하지만 실제 업무 우선순위가 다름 | 계약 또는 의미 평가 |

[문자 문법 실험](visuals.html#grammar)에 ne, neg, negative, banana를 차례로 넣는다. 허용 문자 수와 종료 가능 여부가 달라지는 이유를 설명하게 한다. 완성된 negative가 문법적으로 허용되더라도 입력의 감정이 실제로 negative인지 알 수 없다는 답이 나와야 한다.

원문의 세 그림을 비교해서 설명한다. 6-19는 생성 후 검토, 6-20은 확정된 구조에 값 채우기, 6-21은 다음 후보 제한이다. 생성 시점과 사후 검사 시점을 칠판에 따로 표시한다. GGUF는 파일 형식이며 원문의 fp16 파일을 저비트 양자화라고 부르지 않는다.

## 8교시 실습 76–82분

저장소 루트에서 다음을 실행한다.

```bash
python3 chapters/ch06/lab.py
python3 chapters/ch06/lab.py --temperature 2 --top-p 0.95
```

첫 출력과 두 번째 출력의 분포가 어떻게 바뀔지 먼저 예상하고 실행한다. 다른 모듈은 같은 설정이므로 대부분 그대로이며, 표본 빈도는 바뀐 분포의 영향을 받는다. 정답률을 측정하는 실습이 아니라 계산 구조를 관찰하는 실습임을 학습자가 직접 말하게 한다.

시간이 부족하면 실행 결과를 [lab-output.txt](lab-output.txt)로 대신 보여 주고 실제 실행은 과제로 옮긴다. 이 경우 교사는 수업 중 실행한 것처럼 설명하지 않는다.

## 종료 평가 82–85분

1. “top-p는 무엇을 누적하는가?” — 정렬된 후보의 확률을 누적한다.
2. “JSON 파싱 성공 뒤에 필요한 두 가지 검사는?” — 필드·타입·허용값 검사와 내용·근거 검증.
3. “세 전문가가 등장하는 한 응답이 독립된 세 전문가의 검증인가?” — 아니며 한 모델이 만든 모방일 수 있다.

세 문항 중 두 개 이상 설명하기 어렵다면 관련 [학습 노트](study.md)를 다시 읽고 [복습 문제](quiz.md) 4, 10, 14번을 푼다. 후속 과제는 자신의 업무 하나를 골라 입력 계약과 출력 검증 순서를 작성하는 것이다.
