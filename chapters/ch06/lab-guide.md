## 무엇을 실행하는가

[lab.py](lab.py)는 다음 토큰 분포, 후보 제한, 답 정규화와 다수결, 중간 상태 탐색, 문자 문법, JSON 검증을 실제 계산한다. **실제 LLM을 호출하지 않는다.** 교육용 로짓과 교사가 정한 답 후보를 사용하므로 모델의 정답률이나 생성 품질을 측정하는 실험이 아니다. 인터넷 연결·API 키·GPU·외부 Python 패키지가 필요 없다.

원리 출처는 *Hands-On Large Language Models*, Chapter 6, PDF 물리 페이지 236–279다. 확률 수식, beam search, 문자 trie, JSON 검사 코드는 원리를 관찰하기 위해 새로 작성한 보충 실습이다.

## 실행과 결과 파일

저장소 루트에서 실행한다.

```bash
python3 chapters/ch06/lab.py
python3 chapters/ch06/lab.py --help
```

챕터 폴더 안에서는 `python3 lab.py`로 실행한다. 기본 설정은 temperature=1, top-p=0.8, top-k 제한 없음, seed=6, 표본 2,000개, beam width=2다. 기본 실행의 실제 결과는 [lab-output.txt](lab-output.txt)에 저장되어 있다. 실행은 파일을 수정하지 않고 터미널에 결과를 출력한다. 결과를 새 파일에 보존하려면 원하는 파일 이름으로 출력을 저장하면 된다.

## 1단계 온도와 후보 제한

로짓 `[2,1,0,-1]`에 softmax를 적용한다. 수치가 커져 지수 함수가 넘치는 문제를 줄이기 위해 최대 로짓을 먼저 뺀다. 모든 로짓에서 같은 상수를 빼도 확률은 바뀌지 않는다. 온도는 양수만 허용하며, 잘못된 설정은 실행 시작 단계에서 오류로 알려 준다.

`truncate` 함수의 처리 순서는 top-k, 재정규화, top-p, 재정규화다. 이는 학습을 위해 명시한 순서이며 모든 라이브러리가 반드시 이 순서로 처리한다는 뜻은 아니다. top-p는 정렬된 확률의 누적이 임계값을 넘는 후보까지 포함한다.

기본 실행에서 확인할 값은 다음과 같다.

| 관찰값 | 실제 기본 실행 결과 |
|---|---:|
| T=1에서 A의 확률 | 0.643914 |
| top-p 이후 A의 확률 | 0.731059 |
| top-p 이후 B의 확률 | 0.268941 |
| C와 D의 최종 확률 | 0 |
| 최종 엔트로피 | 약 0.839942 bits |
| 2,000회 추출 빈도 | A 1,477회, B 523회 |

표본 빈도는 확률의 정확한 곱과 일치할 필요가 없다. 예를 들어 A의 기대 횟수는 약 1,462.1회이지만 실제 추출은 1,477회였다. 동일 seed와 이 실행 환경에서는 재현되며, 다른 seed에서는 달라질 수 있다. Python 버전별 난수 관련 동작 차이가 생길 수 있으므로 확률 값과 표본 횟수를 구분해 해석한다.

### 바꿔 볼 실험

```bash
python3 chapters/ch06/lab.py --temperature 0.5 --top-p 1
python3 chapters/ch06/lab.py --temperature 2 --top-p 1
python3 chapters/ch06/lab.py --temperature 2 --top-k 1
python3 chapters/ch06/lab.py --seed 99 --draws 10000
```

낮은 온도에서는 A에 확률이 집중된다. top-k=1이면 최종 확률은 A가 1이 되어 온도의 효과가 최종 후보 선택에서 사라진다. seed를 바꾸면 추출 횟수는 달라지지만 계산된 확률은 그대로다. 먼저 예상 결과를 적고 실행하자.

## 2단계 답의 정규화와 다수결

후보 답은 교사가 만든 `21`, `21자루`, `20`, `21`, `22`다. `normalize_answer`는 정수와 선택적인 자루 단위를 인식한다. 이 실습에서는 21이 3표를 얻는다. 정규식은 모든 자연어 답변을 이해하는 범용 파서가 아니므로, 이 형식을 벗어난 입력은 오류로 처리한다.

독립적인 이진 판단에서 각 답의 정확도가 0.7이라고 가정하면 n=3의 과반수 정답 확률은 0.784, n=5는 0.83692다. 반면 모든 오류가 완전히 상관되어 있다면 반복 수를 늘려도 0.7이다. 이는 **수학적 가정의 비교**다. 실제 모델이 83.692% 정확하다는 결론을 내릴 수 없다.

관찰 질문은 “같은 오답이 항상 반복되는 모델을 열 번 호출하면 무엇이 개선되는가?”다. 서로 독립적인 정보가 늘지 않는다면 단지 호출 비용이 늘 수 있다. 또한 문자열 정규화를 잘못하면 같은 답을 다른 답으로 세거나 다른 답을 하나로 합칠 수 있다.

## 3단계 중간 상태 탐색

시작 상태는 1, 목표는 10, 가능한 연산은 +3과 ×2, 최대 깊이는 3이다. 각 상태의 평가 점수는 목표와의 절대 거리가 작을수록 좋다고 정했다. 가능한 후보는 일반 Python 연산으로 생성하며 LLM이 제안하지 않는다.

| 폭 | 보존 경로의 예 | 결과 |
|---|---|---|
| 1 | 1 → 4 → 8 → 11 | 깊이 3 안에 실패 |
| 2 | 1 → 4 → 7 → 10 | 목표 도달 |

8은 7보다 당장 10에 가깝지만 다음 한 번의 허용 연산으로 10에 갈 수 없다. 즉 현재 거리만 보는 휴리스틱은 최종 도달 가능성을 완벽히 평가하지 않는다. 폭 2는 7도 남겨 두어 성공한다. 더 큰 폭이 모든 문제의 정답 보장을 의미하지는 않는다. 탐색 깊이, 후보 생성, 평가 기준이 함께 영향을 준다.

실제 ToT로 확장할 때 대응 관계는 “상태 = 지금까지의 부분 해법”, “연산 = 다음 후보 제안”, “거리 점수 = 유망성 평가”, “목표 10 도달 = 최종 검증”이다. 자연어 문제에는 정확한 목표 판정기가 없는 경우가 많으므로 평가 자체가 더 어려워진다.

## 4단계 문법 제약

`allowed_next`는 접두사를 주면 positive, neutral, negative로 이어지는 다음 문자를 반환한다. `ne`에는 g와 u가 가능하고, 완성된 `negative`에는 다음 문자가 없지만 종료가 허용된다. `banana`에는 문자도 종료도 허용되지 않는다. 생성기는 허용 문자 안에서만 교육용 가중치로 샘플링하며 마지막에 허용 라벨 집합에 속하는지 검산한다.

이 코드는 문자 단위의 유한 집합 문법이다. 실제 LLM의 토큰은 여러 글자를 포함할 수 있고 JSON 문법은 중첩 구조도 다뤄야 한다. 따라서 이 실습을 그대로 전체 JSON 제약 디코더라고 부를 수는 없다. 대신 “현재 접두사에서 허용되지 않은 전개를 제거한다”는 핵심 원리는 직접 확인할 수 있다.

## 5단계 JSON의 세 종류 검사

`validate_ticket`은 순서대로 JSON 파싱, 정확한 키와 자료형·허용값, 근거 구절의 원문 포함 여부를 검사한다. `json.loads`로 파싱된 뒤에도 priority가 문자열이면 스키마 검사에서 실패한다. JSON의 true는 Python의 bool로 변환되며 bool은 int의 하위형이므로, 정수 필드는 `type(value) is int`로 확인해 true를 통과시키지 않는다.

원문에 없는 “환불 완료”가 evidence이면 근거 검사에서 실패한다. 하지만 근거 문자열이 포함되어 있다는 사실만으로 label과 priority의 업무상 판정이 정확하다고 보장하지는 않는다. 실습의 성공 메시지도 “정의한 검사 통과”라고 제한한다. 더 넓은 의미 검증은 별도의 규칙·정답·사람 검토가 필요하다.

## 6단계 프롬프트 모듈 조립

마지막 부분은 작업, 범주, 형식, 자료를 분리한 뒤 줄바꿈으로 조립한다. 완성된 문자열을 출력하지만 모델에 전송하지 않는다. 어느 구성 요소를 바꾸면 어떤 성공 기준을 평가해야 하는지 말해 보자. 형식을 바꾸면 파싱과 키 일치를, 범주 정의를 바꾸면 정답 라벨과 경계 사례를 확인할 수 있다.

## 원문의 실제 모델 실습으로 확장

원문의 모델 추론과 GPU 로딩은 이 자료에서 실행하지 않았다. 실제로 확장할 때는 다음 순서로 진행한다.

1. 책의 공식 코드 저장소와 사용할 모델의 설명에서 해당 예제의 환경과 이용 조건을 확인한다. 모델 파일과 라이브러리 버전을 함께 기록한다.
2. 모델에 맞는 토크나이저와 chat template를 확인하고, 모델이 받을 입력을 출력해 본다. 원문은 Phi-3-mini instruct를 사용한다.
3. 원문의 기본 생성처럼 변동이 적은 설정에서 작은 정답 자료로 기준 결과를 만든다. 생성 길이, 종료 이유, 입력 길이를 기록한다.
4. 프롬프트 구성 또는 샘플링 설정을 한 번에 하나씩 바꾼다. 정답률, 형식 성공률, 지연을 따로 기록한다.
5. JSON 예시와 문법 제약을 비교하되, 둘 다 파싱과 스키마·내용 검사를 수행한다. 원문의 GGUF 예제는 FP16 파일을 지정한다는 점을 구별한다.
6. 실제 결과와 설정을 새 실험 기록으로 보존하고 이 CPU 실습의 가상 확률과 섞지 않는다.

책의 코드가 현재 설치한 라이브러리에서 그대로 동작한다고 검증한 상태는 아니다. 이 안내는 실제 확장을 위한 작업 순서이며 패키지의 최신 사용법 안내를 대신하지 않는다.
